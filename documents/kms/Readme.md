# AWS KMS (Key Management Service) - Complete Guide

## Overview

AWS Key Management Service (KMS) is a fully managed service used to create, manage, rotate, and protect encryption keys used by AWS services and applications.

### Key Responsibilities of KMS

- Create encryption keys
- Store encryption keys securely
- Rotate encryption keys
- Control access to keys
- Audit key usage via CloudTrail
- Support encryption and decryption operations

---

# High-Level Architecture

```text
User / Application
        |
        v
AWS Service
(S3, EBS, RDS, EFS, DynamoDB, SQS, SNS)
        |
        v
AWS KMS
(Customer Managed Key / AWS Managed Key)
        |
        v
Generate Data Encryption Key (DEK)
        |
        v
Service Encrypts Actual Data
```

---



# Envelope Encryption

```text
KMS Key
    |
    v
Generate Data Encryption Key (DEK)
    |
    v
Service Uses DEK
    |
    v
Encrypt Actual Data
```

---

# Why Envelope Encryption?

Imagine encrypting:

- 10 GB File
- 100 GB File
- 10 TB File

If every byte went through KMS:

Problems:

- High latency
- Higher cost
- Performance bottleneck
- Poor scalability

Therefore:

```text
KMS Protects Keys
Services Encrypt Data
```

---

# Core Components

## 1. KMS Key (CMK)

The master encryption key stored securely inside AWS-managed HSMs.

Examples:

- AWS Managed Key
- Customer Managed Key

---

## 2. Data Encryption Key (DEK)

Temporary AES-256 key generated by KMS.

Used to:

- Encrypt files
- Encrypt database blocks
- Encrypt EBS volumes
- Encrypt messages

# S3 + KMS Complete Flow

## Upload Scenario

Suppose a user uploads:

```text
salary.xlsx
```

to an S3 bucket with SSE-KMS enabled.

---

## Step 1: User Uploads File

```text
User
 |
 v
salary.xlsx
 |
 v
S3 Bucket
(SSE-KMS Enabled)
```

---

## Step 2: S3 Calls KMS

S3 requests:

```json
GenerateDataKey
```

Example:

```json
{
  "KeyId": "abc-123",
  "KeySpec": "AES_256"
}
```

---

## Step 3: KMS Generates DEK

Inside KMS:

```text
Generate Random AES-256 Key
```

Example:

```text
Plaintext DEK

7f9a8c2d4e6b1f8a9c3d5e7f1a2b4c6d
```

KMS then encrypts this DEK using the KMS Key.

```text
Encrypted DEK

AABBCCDDEEFF112233445566...
```

KMS returns BOTH:

```text
1. Plaintext DEK
2. Encrypted DEK
```

---

## Step 4: S3 Encrypts File

```text
salary.xlsx
        +
Plaintext DEK
        =
Encrypted Object
```

Result:

```text
8xY2AbCdEfGhIjKlMnOp...
```

---

## Step 5: S3 Deletes Plaintext DEK

After encryption:

```text
Plaintext DEK
```

is removed from memory.

---

## What Gets Stored?

```text
S3 Bucket
|
|-- Encrypted File
|
|-- Encrypted DEK
```

Example:

```text
Object:
salary.xlsx

Data:
8xY2AbCdEfGhIjKlMnOp...

Metadata:
EncryptedDEK=AABBCCDDEEFF112233...
```

# Why Does KMS Return Plaintext DEK?

This is one of the most common interview questions.

---

## Question

If security is important, why does KMS return the Plaintext DEK?

---

## Answer

Because someone must actually encrypt the data.

If KMS only returned:

```text
Encrypted DEK
```

then S3 could not use it.

---

### Example

Imagine receiving:

```text
Locked Box
```

instead of:

```text
Actual Key
```

You cannot open anything.

Similarly:

```text
Encrypted DEK
```

cannot encrypt data.

---

## Therefore KMS Returns

```text
1. Plaintext DEK
2. Encrypted DEK
```

---

## Purpose of Each

### Plaintext DEK

Used immediately to:

```text
Encrypt File
Encrypt Volume
Encrypt Database Block
Encrypt Message
```

---

### Encrypted DEK

Stored permanently.

Used later during decryption.

---

# Security Model

## Does Plaintext DEK Remain Stored?

No.

Plaintext DEK:

- Exists briefly in memory
- Not written to disk
- Not stored in S3
- Not visible to users

After encryption:

```text
Deleted from memory
```

Only:

```text
Encrypted DEK
```

is stored.

---

# Real Life Analogy

```text
KMS Key = Master Key

DEK = Locker Key
```

Workflow:

```text
KMS Creates Locker Key
        |
        +--> Actual Locker Key
        |
        +--> Locker Key Inside Sealed Envelope
```

S3:

```text
Uses Actual Locker Key
Locks Document
Destroys Actual Key
Stores Sealed Envelope
```

Later:

```text
Bring Sealed Envelope To KMS
        |
        v
KMS Opens Envelope
        |
        v
Returns Locker Key Again
```

# Does Plaintext DEK Leave HSM?

## Yes

During:

```text
GenerateDataKey
```

Inside HSM:

```text
Generate DEK
```

Output:

```text
Plaintext DEK
Encrypted DEK
```

Both are returned.

```text
HSM
 |
 +--> Plaintext DEK
 |
 +--> Encrypted DEK
```

Why?

Because S3/EBS/RDS must perform actual encryption.

# Trainer Tip

Remember this single sentence:

> KMS protects the encryption keys, while services like S3, EBS, RDS, DynamoDB, EFS, SQS, and SNS use Data Encryption Keys generated by KMS to encrypt the actual data.

Understanding this concept explains almost every KMS integration in AWS.

---



```text
KMS Key
     |
Generate DEK
     |
AES-256 DEK
     |
Encrypt 100 GB File
```

KMS protects the key.

The AWS service performs the actual encryption.

This design is called:

ENVELOPE ENCRYPTION
